I have a problem: GAM's photo upload E2E test flakes, but only sometimes, and only when the suite runs in parallel. The feature itself is boring — the backend signs an upload to RustFS (S3-compatible) and writes the URL back to the zone. The race was entirely in the test.

## The pattern

The uploader renders a styled dropzone: a visible label over an `opacity: 0` file input that fills the box.

```tsx
<input
  type="file"
  accept="image/*"
  className="absolute inset-0 z-10 h-full w-full cursor-pointer opacity-0"
  data-testid="file-input"
/>
```

The original test forced the input visible and called `setInputFiles`:

```ts
await page.addStyleTag({ content: '[data-testid="file-input"] { opacity: 1 !important; }' })
await page.getByTestId('file-input').setInputFiles({ name: 'e2e-test.png', mimeType: 'image/png', buffer })
```

Playwright runs tests in parallel with workers sharing one CDP connection. `addStyleTag` mutates the DOM right before the worker resolves the input locator, and under load the node ID goes stale between resolve and dispatch. The call fails, the test flakes.

## Why the clean fix works

Playwright already has a first-class API for file inputs: the `filechooser` event. When the browser opens the OS file dialog, Playwright intercepts it. So instead of mutating the DOM and fighting CDP, you let the browser do its thing and hand it the file through the intercepted dialog:

```ts
const fileChooser = page.waitForEvent('filechooser')
await page.getByTestId('file-input').click({ force: true })
await (await fileChooser).setFiles({
  name: 'e2e-test.png',
  mimeType: 'image/png',
  buffer,
})
```

The `{ force: true }` is the one wrinkle: the `opacity-0` input sits under a transparent `z-10` layer, so Playwright's actionability check refuses to click "through" it. `force` skips that check, the native click fires, the dialog opens, and the `filechooser` event lands. No style injection, no node IDs, no staleness.

A bridge approach also works — expose a `window.__uploadZonePhoto` handler and call it via `page.evaluate` — but that ships test-only code into the component and couples the test to an internal handler. The `filechooser` API is the real user flow, minus the actual OS picker: click the dropzone, pick a file, done.

## The backend side

While debugging the test I found the backend dedupes photos at the domain level. The Zone entity's `addPhoto` checks the URL before appending:

```typescript
addPhoto(photoUrl: string): void {
  if (this._photos.includes(photoUrl)) return;
  this._photos.push(photoUrl);
}
```

The S3 upload uses `p-retry` with 3 retries and exponential backoff, and the `zones:all` / `zone:{id}` caches are evicted after every successful upload so the new photo shows immediately.

## The takeaway

The race was in the test infrastructure, not the app — GAM is single-user, concurrent uploads aren't a production concern. The fix that's *correct* isn't always the fix that's *first*: the global bridge passed, but left production code polluted for a test. Playwright's `filechooser` API was the clean answer the whole time. It just took going through the hack to appreciate it.
